# 📘 Lecture – Reference, Populate & Thought Process of Writing APIs

## Overview
Is lecture mein hum:
- `ref` aur `populate` ka concept samajhte hain  
- Connection Request ke **review APIs** design karte hain  
- API likhne ka **proper thought process** seekhte hain  
- Connections API build karne ka foundation banate hain  

---

## What is `ref` in Mongoose?

`ref` ka use tab hota hai jab:
- Ek document doosre document se related hota hai  
- Hum sirf **ID store** karte hain, poora data nahi  

Example context:
- Connection Request document ke andar:
  - `fromUserId`
  - `toUserId`
- Ye dono **User collection** ko refer karte hain  

Isse fayda:
- Data duplicate nahi hota  
- Database normalized rehta hai  
- Storage kam use hota hai  

---

## Why `ref` is Important

Agar hum poora user data connection request mein store karein:
- Data duplicate hoga  
- Update karna mushkil ho jayega  
- Inconsistency aa sakti hai  

Isliye:
> **Sirf reference (ID) store karna best practice hai**

---

## What is `populate`?

`populate` ka kaam:
- Reference ID ko actual document data se replace karna  

Simple words mein:
- Pehle sirf `userId` milta hai  
- `populate` ke baad user ka:
  - name  
  - email  
  - photo  
  - skills  
  mil jata hai  

---

## Why Populate is Important in Real Apps

Without populate:
- Sirf IDs milti hain  
- Frontend ko baar-baar extra API calls karni padti hain  

With populate:
- Ek hi API se complete data  
- Performance better hoti hai  
- Response clean aur readable hota hai  

---

## Connection Request – Review API Concept

Review API ka matlab:
- User apne paas aayi hui connection requests par action leta hai:
  - accept  
  - reject  
  - ignore  

Ye API **dynamic status change** karti hai.

---

## Allowed Status Values

Connection request ka status sirf in values mein se ho sakta hai:
- `interested`
- `ignored`
- `accepted`
- `rejected`

Enum ka use isliye hota hai taaki:
- Invalid status database mein na jaaye  
- State transitions controlled rahein  

---

## Important Business Logic (Very Important)

User **ignore / accept / reject** tabhi kar sakta hai jab:
- Uske paas already ek request aayi ho  
- Request ka current status `interested` ho  

❌ Invalid cases:
- Request already `accepted` ho  
- Request already `rejected` ho  
- Request already `ignored` ho  

In sab cases mein:
- Review action allow nahi hona chahiye  

---

## Thought Process While Writing Review API

API likhne se pehle hamesha socho:

1. User logged-in hai ya nahi?  
2. Connection request exist karti hai ya nahi?  
3. Request isi user ke liye hai ya nahi?  
4. Current status kya hai?  
5. Requested action allowed hai ya nahi?  
6. Same request dobara update toh nahi ho rahi?  

Ye sab validations **API level par** hone chahiye.

---

## Why Review API Must Be Protected

Review API:
- Sirf logged-in user hi call kar sakta hai  
- Auth middleware mandatory hota hai  
- JWT se user ki identity milti hai  

Isse:
- Koi doosra user request manipulate nahi kar sakta  

---

## After Review APIs – Connections API

Review APIs ke baad next step hota hai:
### Connections API

Connections API ka kaam:
- User ke **current connections** dikhana  
- Sirf `accepted` requests consider karna  

---

## Connections API – High Level Idea

Connections API:
- Connection Request collection se data uthata hai  
- Condition:
  - Status = `accepted`  
- Dono taraf ke users ko populate karta hai  

Isse user dekh sakta hai:
- Uske active connections kaun-kaun se hain  

---

## Logic to Fetch User Connections (Thought Process)

User ke connections nikalne ke liye:
- Do cases consider hote hain:
  - User `fromUserId` ho  
  - User `toUserId` ho  

Logic:
- Jahan bhi logged-in user involved ho  
- Aur status `accepted` ho  
- Wahi real connection mana jata hai  

---

## Why Separate Review & Connections APIs?

Review API:
- Action perform karti hai (accept / reject / ignore)

Connections API:
- Sirf data read karti hai  

Separation se:
- Code clean hota hai  
- Responsibility clear hoti hai  
- Bugs kam hote hain  

---

## Populate in Connections API

Connections API mein populate use hota hai taaki:
- Sirf IDs nahi  
- Full user details milen  

Common fields:
- Name  
- Profile photo  
- Skills  

---

## Key Takeaways

- `ref` document relationships ko represent karta hai  
- `populate` IDs ko real data mein convert karta hai  
- Review APIs strict business rules follow karti hain  
- Status transitions controlled hone chahiye  
- Auth middleware mandatory hota hai  
- Connections API sirf accepted requests dikhati hai  
- Proper thought process API bugs kam karta hai
